# Update - 3 September 2026

## Headline result

The orbit fit was never going to converge. After fixing two genuine bugs and
building an independent orbit-determination path, the conclusion is:

> **The three detections (IRAS 1983, AKARI 2006-10-26, AKARI 2007-04-23) are
> mutually inconsistent with any single two-body orbit — bound or hyperbolic —
> at any distance from 20 AU to 50,000 AU.**

This is a property of the **data**, not a failure of the sampler. The best
achievable residual is ~922 arcsec, against an assumed astrometric uncertainty
of 5 arcsec.

The inconsistency is localised to the **two AKARI epochs**, and — importantly —
it is confined to **RA alone**. Declination behaves exactly as it should.

| Quantity (AKARI_1 -> AKARI_2, 179 days) | dRA*cos(dec) | dDec |
|---|---|---|
| **Observed** | **+1224.1 arcsec** | **+458.6 arcsec** |
| Parallax prediction at 200 AU | -2010.2 | **+459.9** |
| Parallax prediction at 270 AU | -1488.9 | +341.2 |
| Parallax prediction at 500 AU | -804.0 | +184.6 |
| Best over all distances (100,000 AU) | -4.0 | +0.9 |

Fitting each coordinate **separately** makes this unambiguous:

```
Dec  best distance =     200.5 AU   predicted  +458.7 vs observed  +458.6   gap    0.0 arcsec   CONSISTENT
RA   best distance =  100000.0 AU   predicted    -4.0 vs observed +1224.1   gap 1228.1 arcsec   NO SOLUTION
```

This is a much sharper result than a generic "bad fit":

- **Declination is essentially perfect.** It is solved exactly by a stationary
  object at **200.5 AU** — predicted +458.7 vs observed +458.6 arcsec, a gap of
  **0.0 arcsec**. The Dec data behave precisely like a real distant object.
- **RA has the wrong sign.** At that same distance the prediction is
  **-2010 arcsec**, but the data show **+1224 arcsec**. Between late October
  and late April the Earth moves to the opposite side of its orbit, so a
  distant object **must** shift in the opposite RA sense. The RA-only fit is
  driven to 100,000 AU and still leaves a 1228 arcsec gap: no choice of
  distance can repair a sign error.

A single distance that satisfies Dec and grossly violates RA points to a
**problem in the RA coordinate of one AKARI detection**, not to a bad orbit.

## Part 1 - Changes to `run_orbit-mcmc.py`

### 1.1 Fixed the IRAS observer position (correctness bug)

**Location:** `load_iras_observer_state()`

**What was wrong.** The header row of `iras-pos.csv` is shifted relative to its
data. The file stores an extra unnamed magnitude column after each xyz triplet,
so the columns *labelled* `x-sat-geo / y-sat-geo / z-sat-geo` do not actually
contain the geocentric offset. Reading them by name produced an offset of
**0.9866 AU (~147 million km)** — the code was placing IRAS roughly a full
astronomical unit away from Earth.

**The fix.** Columns are now read **positionally**, and the geocentric offset is
recomputed from the two heliocentric vectors that the file does store correctly:

```
0     jd
1-3   satellite heliocentric xyz (km),  4  |r|
5-7   Earth     heliocentric xyz (km),  8  |r|
9-11  satellite geocentric   xyz (km), 12  |r|
```

```python
geo_offset_km = values[best_idx, 1:4] - values[best_idx, 5:8]
```

This reconstruction agrees with columns 9-11 to within 0.001 km, which is a
strong internal consistency check on the interpretation.

**Guard rail added.** A hard failure is raised if the offset is ever implausible
again, so a future change to the file layout cannot silently reintroduce the bug:

```python
if offset_magnitude_km > 1.0e5:
    raise ValueError(...)
```

**Why we need it.** IRAS was in a ~900 km Sun-synchronous orbit. A 1 AU error in
the observer position is the same size as the entire parallax baseline, so it
corrupts the single most informative geometric constraint in the fit.

**Verified output** (from `diagnose_geometry.py`, section `[E]`):

```
IRAS 1983      offset from Earth centre = 7,275.9 km  (satellite altitude 898 km)
AKARI_1 2006   offset from Earth centre = 7,092.6 km  (satellite altitude 715 km)
AKARI_2 2007   offset from Earth centre = 7,094.6 km  (satellite altitude 717 km)
```

All three are now plausible low-Earth-orbit radii.

**Honest note on impact:** this bug was real but was **not** the cause of the bad
fit. RMS residual moved only from 735 -> 724 arcsec.

### 1.2 Fixed a heliocentric / barycentric frame mismatch

**Location:** just after `observer_positions_au` is assembled, and in the
`observer_positions_au is None` default branch of `keplerian_sky_coordinates()`

**What was wrong.** The model propagates a **heliocentric** two-body orbit — it
uses `mu = GM_sun`, so the returned positions are measured from the **Sun**. But
the observer vector being subtracted was **barycentric** (measured from the solar
system barycentre). Subtracting vectors defined from two different origins is
simply incorrect.

**The fix.**

```python
observer_positions_au = observer_positions_au - get_body_barycentric(
    "sun", observation_times
).xyz.to_value(u.au).T
```

and correspondingly in the fallback path:

```python
observer_positions_au = (
    get_body_barycentric("earth", times).xyz.to_value(u.au).T
    - get_body_barycentric("sun", times).xyz.to_value(u.au).T
)
```

**Why we need it.** The Sun-barycentre separation is driven mainly by Jupiter and
reaches **0.0098 AU**. At 270 AU that is about **7 arcsec** — larger than the
5 arcsec/coordinate uncertainty the likelihood assumes. It would have biased any
final solution even though it is far too small to explain the present residuals.

The same fix was applied to `run_orbit-free_params.py` and
`Fixed_a/run_orbit-fixed_a.py` so all three fitters share one convention.

### 1.3 New: command-line interface

```python
parser.add_argument("--seed", type=int,   default=RANDOM_SEED)
parser.add_argument("--init", choices=["ball", "prior"], default=INIT_MODE)
parser.add_argument("--tag",  type=str,   default="")
```

- `--seed` controls walker initialisation, making runs reproducible.
- `--init` selects the starting distribution (see 1.4).
- `--tag` appends a suffix to every output filename, so competing runs do not
  overwrite each other and can be compared side by side.

**Why we need it.** When a fit fails, the first question is always *"is this a
real result or an artefact of where the sampler started?"* Being able to vary
the seed and the start mode from the shell — without editing the source —
is what turns that question into a one-line experiment.

Example:

```powershell
python run_orbit-mcmc.py --seed 7 --init prior --tag dispersed
```

### 1.4 New: `build_initial_positions()` with two start modes

Walker initialisation was extracted into its own function offering:

- **`ball`** — a tight Gaussian cloud around the previously reported best fit
  (a = 2000 AU, e = 0.866, i = 30.94 deg, ...), with `np.clip` and angle wrapping
  so no walker can be born outside the prior (which would give it
  `-inf` posterior and effectively kill it).
- **`prior`** — walkers drawn across the entire prior volume, with the
  semi-major axis sampled **log-uniformly** (`np.exp(rng.uniform(np.log(A_MIN),
  np.log(A_MAX)))`) because *a* spans more than a decade and a linear draw would
  crowd every walker into the large-*a* end.

**Why we need it.** These two modes bracket the diagnosis. If `ball` and `prior`
converge to the same place, the answer is robust. If only `ball` finds a good
fit, the posterior is start-dependent. In our case **both fail identically**,
which was the first strong hint that the problem was the data.

### 1.5 New: `format_diagnostics()` - the core addition

This is the most important new component. Previously the script printed a
posterior summary with confident-looking error bars and no indication of whether
the fit was meaningful at all. It now emits four checks.

#### [1] Acceptance fraction

```
mean = 0.3072   min = 0.0074   max = 0.3928
STATUS: OK
```

Fraction of proposed steps accepted. Healthy is roughly 0.2-0.5. Too low means
the sampler is stuck; too high means it is taking steps so small it is not
exploring. **Ours is healthy — so emcee is working correctly.** This is what
lets us rule out "the sampler is broken" as an explanation.

#### [2] Integrated autocorrelation time

```
a(AU)  tau = 494.21   50*tau = 24710.4   N_eff = 259.0
...
Chain length = 5000 steps; max(50*tau) = 27122.2
STATUS: WARNING - chain too short / not converged
```

`tau` measures how many steps the chain takes to forget where it was. The
standard requirement is `n_steps > 50*tau`. We report `tau`, the required length,
and the **effective sample size** per parameter. The `try/except` around
`sampler.get_autocorr_time()` catches emcee's `AutocorrError` and falls back to
`quiet=True`, so an unconverged chain still produces a number and a warning
rather than crashing the run.

**Interpretation:** the chain would need ~27,000 steps, not 5,000. Worth knowing,
but secondary — a longer chain cannot rescue a fit whose best possible residual
is 145 sigma.

#### [3] Goodness of fit at the maximum-posterior sample

This is the check that exposed the real problem.

```
RMS residual  = 723.501 arcsec
Max residual  = 1293.377 arcsec
Assumed sigma = 5.0 arcsec/coordinate
chi^2         = 1.2563e+05
N_data = 6, N_params = 6, dof = 0
NOTE: dof = 0 (exactly determined system).
      A correct solution should give residuals at the noise level.
STATUS: FAIL - residual is 145x the assumed sigma.
        The sampler has NOT found a valid orbit solution.
Per-coordinate residuals (arcsec):
  RA_1         86.780
  RA_2       1206.004
  RA_3      -1293.377
  Dec_1        58.796
  Dec_2       -10.912
  Dec_3       -48.449
```

Two things make this powerful:

**The `dof = 0` argument.** Six observations (3 detections x RA/Dec) and six free
parameters means the system is *exactly determined*. There is no
least-squares compromise to make: a correct model must pass essentially
**through** all six numbers. So any residual far above the noise floor is proof
of inconsistency, and the code says so explicitly rather than leaving it to the
reader.

**Per-coordinate breakdown.** The aggregate RMS hides the structure; the
breakdown reveals it immediately. `RA_2 = +1206` and `RA_3 = -1293` are large and
**opposite in sign**, while all three Dec residuals are small. That signature —
the fit splitting the difference between two irreconcilable RA values at the two
AKARI epochs — is what pointed directly at the AKARI parallax sign problem.

#### [4] Prior boundary contact

```
a lower (200 AU)     fraction within 1% of edge =  0.0000   ok
a upper (5000 AU)    fraction within 1% of edge =  0.0000   ok
e upper (0.90)       fraction within 1% of edge =  0.8118   WARNING - prior-driven
```

Reports the fraction of the posterior sitting within 1% of each prior edge. If a
"measurement" is really just the prior wall, that must not be reported as a
constraint.

**Interpretation:** 81% of samples are jammed against `e < 0.9`. The quoted
`e = 0.8999 (+0.00006 / -0.015)` is **not a measurement** — the sampler is
pushing eccentricity as high as it is allowed in a futile attempt to reconcile
the three points. Without this check that number looks like a precise result.

### 1.6 New: `save_trace_plot()`

Plots all 32 walkers for all 6 parameters against step number, with a red dashed
line marking the end of burn-in.

**Why we need it.** Traces are the fastest visual check for the failure modes
`tau` only summarises numerically: walkers stuck on separate plateaus (multiple
modes), a chain still drifting at the end (burn-in too short), or walkers frozen
against a prior edge. Complements [2] and [4].

### 1.7 Tagged, timestamped outputs

```python
suffix = f"_{args.tag}" if args.tag else ""
timestamp_str = datetime.datetime.now().strftime("%Y%m%d_%H%M%S") + suffix
```

Every run now writes five artefacts:

| File | Contents |
|---|---|
| `mcmc_samples_<ts>.csv` | full posterior, angles in degrees |
| `mcmc_corner_<ts>.png` | corner plot (M omitted) |
| `mcmc_traces_<ts>.png` | walker traces incl. burn-in |
| `mcmc_summary_<ts>.txt` | median +/- 68% credible intervals |
| `mcmc_diagnostics_<ts>.txt` | the four checks above, with seed and init mode recorded in the header |

Recording seed and init mode inside the diagnostics file means any saved run can
be reproduced exactly.

## Part 2 - New standalone scripts

### 2.1 `diagnose_geometry.py`

Isolates the observing geometry from the orbit model entirely, so the data can be
tested without any fitting. Six sections:

- **[A]** size of the heliocentric-vs-barycentric offset (motivated fix 1.2)
- **[B]** size of the neglected light-travel-time effect (~1.2 arcsec — real but
  negligible here)
- **[C]** observed AKARI_1 -> AKARI_2 motion vs the parallax prediction at a
  range of trial distances
- **[D]** a scan asking whether **any** distance reproduces the observed motion,
  plus a **per-coordinate fit** that isolates which coordinate is at fault
- **[E]** the observer positions actually in use, expressed as satellite altitude
- **[F]** independent validation of those observer positions (see below)

Section **[D]** is the model-independent core of the whole investigation. It uses
only the observed unit vectors and the observer positions — **no orbit model, no
fitting** — and finds:

```
Best stationary-object distance: 100000.0 AU
Predicted motion: dRA*cos(dec) = -4.0, dDec = +0.9 arcsec
Observed  motion: dRA*cos(dec) = +1224.1, dDec = +458.6 arcsec
Residual mismatch: 1310.6 arcsec
=> NO distance reproduces the observed motion by parallax alone.

Fitting each coordinate separately:
  Dec  best distance =     200.5 AU   gap    0.0 arcsec   CONSISTENT
  RA   best distance =  100000.0 AU   gap 1228.1 arcsec   NO SOLUTION
```

The joint fit is dominated by the RA error and is pushed to an absurd distance,
which hides the real structure. The **per-coordinate fit** was added precisely
for that reason: it shows Dec is not merely "acceptable" but solved *exactly* at
a sensible distance, which converts a vague "the data are bad" into a specific,
testable claim about one coordinate of one detection.

Section **[F]** answers the question "how do we know `obs_pos` itself is right?"
It locates Neptune, Uranus and Saturn two independent ways — (a) barycentric
ephemeris minus our observer vector, (b) astropy's geocentric `get_body` — and
compares:

```
-- neptune
   IRAS 1983      dRA =    -7.10  dDec =    +0.09 arcsec
   AKARI_1 2006   dRA =    -0.91  dDec =    -0.30 arcsec
   AKARI_2 2007   dRA =    +9.82  dDec =    +3.17 arcsec
-- uranus
   IRAS 1983      dRA =   -11.22  dDec =    +1.33 arcsec
   ...
```

Agreement at the 7-17 arcsec level is exactly what the low-precision `builtin`
ephemeris plus neglected light-time predicts. This **rules out a sign error or a
1 AU error in the observer vectors** — which matters, because the injection test
in 2.2 is self-consistent and could not have caught such an error on its own.

### 2.2 `solve_herget.py`

An independent orbit determination via **Herget's method**, written to answer one
question: *is the bad fit a search failure, or is there genuinely no solution?*

**How it works.** Rather than optimising 6 orbital elements, it exploits the true
dimensionality of the problem:

1. Guess the topocentric distances `rho1` and `rho3` at the **first and last**
   epochs. Combined with the observed lines of sight, this fixes two complete
   3-D heliocentric position vectors.
2. Solve **Lambert's problem** for the unique orbit connecting them in the known
   24.00-year flight time (universal-variable formulation, bisection on `z`,
   both prograde and retrograde branches).
3. Propagate that orbit to the **middle** epoch and compare with the observed
   RA/Dec.

That leaves **2 unknowns and 2 residuals**, so a 2-D grid scan finds *every*
solution. This is a fundamentally stronger statement than an optimiser reporting
"I did not find one".

**Three layers of validation** — necessary before any negative result can be
believed:

1. **Solver self-test.** Build known orbits, propagate, then confirm Lambert
   recovers the original velocity:
   ```
   near-circular 230 AU   OK  relative velocity error = 5.186e-11
   eccentric 230 AU       OK  relative velocity error = 1.344e-11
   eccentric 500 AU       OK  relative velocity error = 1.221e-09
   ```
2. **Closed-loop injection test.** A known bound orbit (a = 282.8 AU, e = 0.278,
   i = 101.0 deg) generates synthetic detections **at the three real epochs from
   the three real observer positions**, then goes through the identical search:
   ```
   True distances: rho1 = 361.2876 AU, rho3 = 361.2866 AU
   RESULT: INJECTED SYNTHETIC ORBIT
     residual at middle epoch: 0.0000 arcsec
     distance recovery error: rho1 7.663e-06 AU, rho3 1.596e-07 AU
   ```
   The method recovers a known answer perfectly.
3. **Hyperbolic orbits included.** The propagator handles `a < 0` via hyperbolic
   anomaly, so the search is not artificially restricted to bound orbits.

**Result on the real data:**

```
Scanning 160x160 grid in (rho1, rho3) from 20 to 50000 AU ...
Best grid point: rho1 = 21.01 AU, rho3 = 45313.61 AU  ->  1315.72 arcsec
RESULT: REAL DETECTIONS (IRAS + AKARI x2)
  residual at middle epoch: 921.9668 arcsec
  implied orbit: e = 1.003290 (UNBOUND)
```

The same machinery that nails an injected orbit to 0.0000 arcsec cannot get below
~922 arcsec on the real data anywhere in the search volume, and the least-bad
solution is unbound and pinned to the search boundary.

## Part 3 - Environment issue found

**`scipy.optimize.least_squares` crashes the Python process** in the `astro_env`
conda environment. It is not related to this project's code — it reproduces on a
trivial two-parameter problem:

```python
least_squares(lambda p: np.array([p[0]-1.0, p[1]-2.0]), x0=np.array([0.0, 0.0]))
```

Exit code `0xC06D007F`, no Python traceback (native crash). `scipy.optimize.minimize`
is unaffected.

**Workaround.** `solve_herget.py` uses a hand-written damped Newton solver with a
finite-difference Jacobian, backtracking line search, and clipping to a physical
distance range. Anything else in your stack calling `least_squares` will also
die, so this is worth repairing at the environment level (likely a MKL/LAPACK
version conflict).

## Part 4 - Known limitation, not yet addressed

**Fitted `i` and `Omega` are equatorial, not ecliptic.** The rotation matrix in
`keplerian_sky_coordinates()` builds the orbit in the frame its elements are
defined in, but the observer vector is equatorial (ICRS).

This does **not** degrade the fit — the six elements are free, and the set of
Keplerian orbits is closed under rotation, so the model can represent the truth
exactly. But it means the reported **i = 31.2 deg is referred to the celestial
equator, not the ecliptic**, and must be converted before being compared with
published Planet Nine predictions (which are quoted in ecliptic elements).

Left as-is deliberately: it is a reporting/interpretation issue, and changing the
convention now would only obscure the data problem above.

## Part 5 - Suggested next step

The likely culprit is the **RA of `AKARI_2`, `(124.4695, 14.46484)`**, defined in
`special_points` in each fitting script.

Placing the object on the AKARI_1 line of sight at a trial distance `d` and
predicting where it should appear at the AKARI_2 epoch gives:

```
   d(AU)   predRA(deg)  predDec(deg)   DecResid(as)
     190    123.51159      14.47188          25.3
     200    123.54195      14.46519           1.3   <-- Dec matches
     210    123.56941      14.45914         -20.5
     300    123.73417      14.42277        -151.5

AKARI_2 catalogue: RA=124.46950 Dec=14.46484
```

**Declination independently pins the distance to ~200 AU** (residual 1.3 arcsec).
At that distance the object should have been at **RA = 123.542 deg**, but the
catalogue entry says **124.470 deg** — a discrepancy of **+0.93 deg**, in the
opposite direction to the required motion.

Most probable explanations, in order:

1. the **RA of one AKARI detection is wrong** (transcription, or a wrong
   cross-match to the source list);
2. the two AKARI epochs were **swapped** during extraction;
3. `AKARI_2` is a **different source**, not a redetection of the same object.

Worth doing next:

- check the AKARI source catalogue for what actually lies near
  **RA 123.54, Dec 14.465** at the 2007-04-23 epoch — if a source is there, the
  candidate becomes a ~200 AU object and everything closes;
- rerun `solve_herget.py` with the corrected RA; a real solution should drop the
  residual from ~922 arcsec to the noise level, and the injection test already
  proves the solver will find it if it exists;
- confirm the sign convention used when the AKARI positions were originally
  extracted, since a reversed RA offset would produce exactly this signature.

Until one of these resolves, **the posterior from `run_orbit-mcmc.py` should not
be quoted as an orbit** — the diagnostics correctly label it `STATUS: FAIL`.
